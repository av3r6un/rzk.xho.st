# RZK

## Деплой через Docker Compose

На сервере нужны Docker Engine и Docker Compose v2. Один Dockerfile собирает два образа: Python-бэкенд и Nginx со сборкой Vue. Публичный порт открывает Nginx. Он раздаёт Vue, передаёт запросы `/api/` и `/auth/` в бэкенд и поддерживает WebSocket и потоковое скачивание.

### Запуск из исходников

1. Если файла `.env` ещё нет, выполните `cp example.env .env`. Задайте в нём случайный `SECRET_KEY` длиной не менее 32 байт, например с помощью `openssl rand -hex 32`. При необходимости измените `HTTP_PORT` (по умолчанию 8090).
2. Для переноса существующей базы остановите приложение, сделайте резервную копию SQLite и поместите её в `data/app.db` перед первым запуском. Для чистой установки приложение создаст базу в этом каталоге. Compose использует собственный путь к SQLite внутри контейнера.
3. Соберите образы и запустите сервисы.

```sh
docker compose up -d --build
docker compose ps
curl -fsS http://localhost:8080/health
```

Бэкенд выполняет `alembic upgrade head` при старте. Откройте `http://<адрес-сервера>:8080`, заменив порт, если меняли его в `.env`. Для создания пользователя выполните `docker compose exec backend python create_user.py username`. Журналы запуска доступны через `docker compose logs backend frontend`, журнал запросов бэкенда через `docker compose exec backend tail -n 100 logs/all.log`.

### Тестовая сборка без FFmpeg

Задайте `INSTALL_FFMPEG=0` и отдельный `IMAGE_TAG`, например `test-no-ffmpeg`, в `.env` **до** сборки и снова выполните `docker compose up -d --build`. При таком запуске доступны исходные видео и отдельные субтитры. Для сборки MP4 с дорожкой субтитров нужен образ с `INSTALL_FFMPEG=1`. Параметр действует только при сборке образа.

### Сборка и публикация в Docker Hub

В `.env` укажите имя пользователя или организации Docker Hub в `DOCKERHUB_NAMESPACE`, тег релиза в `IMAGE_TAG` и нужное значение `INSTALL_FFMPEG`. Создайте репозитории `rzk-backend` и `rzk-frontend` в указанном пространстве имён. Собирайте на машине с той же архитектурой, что и сервер.

```sh
docker login
docker compose build
docker compose push
```

### Автоматическая публикация через GitHub Actions

1. В GitHub включите **Allow merge commits** и **Allow auto-merge**. Для ветки `master` задайте обязательную проверку `Docker smoke test` из workflow **CI and PR**. Если нужно автоматически удалять слитые ветки, включите **Automatically delete head branches**.
2. Добавьте секрет репозитория `AUTOMATION_TOKEN` с доступом к этому репозиторию и правами **Contents: Read and write** и **Pull requests: Read and write**. Workflow использует этот токен, чтобы GitHub запускал workflow для PR, созданных и слитых автоматизацией.
3. Создайте GitHub Environment `publish`, разрешите деплой из `master` и добавьте секреты `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`. Токен Docker Hub должен иметь право записи в оба репозитория. Для публикации в организации задайте переменную `DOCKERHUB_NAMESPACE` с её именем.

При push в рабочую ветку CI собирает оба образа и запускает Compose со свежей SQLite и `INSTALL_FFMPEG=0`. После успешной проверки он создаёт или находит PR в `master` и включает автомердж. GitHub сливает PR после выполнения правил защиты ветки. Слияние PR в `master` запускает повторный smoke-тест на коммите слияния и публикацию образы `rzk-backend` и `rzk-frontend` для Linux x86-64 с тегом `sha-<полный SHA коммита>`. Для текущей вершины `master` workflow также обновляет `latest`. В опубликованный бэкенд входит FFmpeg. Публикацию можно повторить вручную из `master` через **Actions → Publish Docker images**.

### Запуск опубликованного релиза

На сервер скопируйте `docker-compose.yml` и `example.env`, настройте `.env` по шаблону и задайте те же `DOCKERHUB_NAMESPACE` и `IMAGE_TAG`, что при публикации. Для приватных репозиториев выполните `docker login` на сервере.

```sh
docker compose pull
docker compose up -d --no-build
docker compose ps
curl -fsS http://localhost:8080/health
```

Для обновления сделайте резервную копию SQLite, укажите новый `IMAGE_TAG` и повторите команды запуска опубликованного релиза. Каталог `data/` сохраняется при пересоздании контейнеров.

## HDRezka API

Примените миграции командой `uv run alembic upgrade head`, затем запустите сервер через `uv run python main.py`.

Для всех маршрутов ниже передавайте `Authorization: Bearer <access_token>`. Токен выдаёт существующий `POST /auth/`. Успешный ответ содержит результат в поле `body`.

| Метод и путь | Тело запроса | Результат |
| --- | --- | --- |
| PUT /api/rezka/cookies | `{"data":{"cookies":"name=value; another=value"}}` | Сохранение куки текущего пользователя |
| GET /api/rezka/cookies | | Статус настройки куки |
| DELETE /api/rezka/cookies | | Удаление куки |
| POST /api/rezka/media | `{"data":{"url":"https://rezka.fi/series/thriller/1741-mentalist-2008-latest.html"}}` | Карточка медиа. HTTP 201 при создании, 200 для сохранённой ссылки |
| GET /api/rezka/media/{uid} | | Карточка медиа по внутреннему UID |
| POST /api/rezka/media/{uid}/streams | `{"data":{"translator_id":238,"season":1,"episode":1}}` | Списки доступных качеств и субтитров с UID |

Карточка содержит числовой `id` от Rezka, внутренний строковый `uid`, а также `category`, `url`, `name`, `original_name`, `cover`, `slogan`, `release`, `country`, `genres` и `translators`. Каждая озвучка содержит `id` от Rezka и `title`. Поле `release` содержит Unix timestamp в секундах на полночь UTC или `null`.

Бэкенд сохраняет одну карточку на ID Rezka в таблице `media`. Поиск по ссылке добавляет запись в `search_history` или обновляет её `updated_at`. Получение карточки и стримов по UID требует записи в истории пользователя. Метаданные старых карточек загружаются при первом обращении.

Для фильма укажите только `translator_id`. Для сериала передавайте также сезон и эпизод. Бэкенд принимает ссылки на `https://rezka.fi` и `https://hdrezka.ag`, сохраняет путь в карточке и отправляет запросы с куки только на `https://rezka.fi`. Куки хранятся в базе в открытом виде и не возвращаются через API.

## Скачивание MP4

Бэкенд выдаёт тикеты и передаёт MP4 и субтитры через RZK. Один MP4 с дорожкой субтитров собирает сервер через FFmpeg.

### Сценарий пользователя

1. Пользователь выбирает озвучку, сезон и серию для сериала, качество и язык субтитров. Значение `subtitles_uid: null` означает скачивание без субтитров.
2. По кнопке «Скачать» бэкенд RZK получает выбранный MP4 у CDN. Запрос за файлом выполняет тот же сервер, который получил ссылку.
3. Без субтитров браузер сохраняет исходный MP4. При выбранном языке пользователь запускает подготовку MP4, видит прогресс и скачивает готовый файл с переключаемой дорожкой отдельной кнопкой.

FFmpeg копирует исходные видео- и аудиодорожки без перекодирования. Если субтитры пришли как SRT или WebVTT, FFmpeg переносит текст и таймкоды в MP4-дорожку `tx3g`. Доступность этой дорожки при воспроизведении зависит от плеера.

### Контракт API

| Маршрут | Назначение |
| --- | --- |
| `POST /api/rezka/media/{uid}/downloads` | Создать короткоживущее разрешение на загрузку. Передать Bearer-токен и поля выбора в обёртке `data` |
| `GET /api/rezka/downloads/{ticket}/video` | Отдать выбранный MP4 потоком с `Content-Type: video/mp4` |
| `GET /api/rezka/downloads/{ticket}/prepare` | WebSocket запускает подготовку MP4 и передаёт прогресс. |
| `GET /api/rezka/downloads/{ticket}/mp4` | Скачать готовый MP4 с дорожкой субтитров. |
| `GET /api/rezka/downloads/{ticket}/subtitles` | Отдать выбранную дорожку. Для загрузки с `subtitles_uid: null` маршрут недоступен |

Пример тела запроса для скачивания без субтитров:

```json
{"data":{"video_uid":"AbCdEf12345678","subtitles_uid":null}}
```

Маршрут `/streams` возвращает `body.streams` и `body.subtitles`. Элементы обоих списков имеют поля `uid` и `title`. Ссылки CDN хранятся в таблице `download_sources` с владельцем, медиа, типом и сроком действия. Повторный запрос с теми же пользователем, медиа, озвучкой, сезоном и серией возвращает действующие источники из БД. Когда действующих видео больше нет, сервер снова запрашивает HDRezka. Манифесты и дубли исключаются. Для видео используется метка `:YYYYMMDDHH:` в UTC+3, для субтитров — Unix timestamp в девятом сегменте пути с конца. Для основного и запасного URL сроки учитываются отдельно.

Маршрут `/downloads` выдаёт тикет по UID текущего пользователя и медиа. Истёкшая запись возвращает HTTP 410, отсутствующая — HTTP 404. Очистка удаляет полностью истёкшие записи при запуске и каждый час. Видео и субтитры выбираются из одного ответа `/streams`.

При успехе POST возвращает HTTP 201 и поля `body.video_url`, `body.subtitles_url`, `body.prepare_url` и `body.mp4_url` (все три `null` без субтитров), `body.filename` и `body.expires_at` (Unix timestamp в секундах). Первый запрос к CDN происходит на GET по тикету. Бэкенд может попробовать запасной URL до отправки заголовков клиенту. Куки HDRezka остаются на сервере. Для запросов к CDN проверяются HTTPS и публичные IP. Исходный хост берётся из ответа HDRezka. Каждый редирект проходит ту же проверку HTTPS и публичных IP, включая переходы между разными доменами CDN.

Тикет действует до 10 минут, в пределах срока действия выбранных источников. GET использует только тикет и поддерживает повторные запросы. Тикеты хранятся в памяти процесса. При нескольких воркерах запросы POST и GET для одного тикета должны попадать в один процесс.

На обратном прокси отключите буферизацию и исключите пути `/api/rezka/downloads/` из журналов запросов.

### Передача исходных файлов с сервера

- Передавать тело через `aiohttp.web.StreamResponse` ограниченными порциями, например по 256 КиБ, с ожиданием завершения каждой записи. Так скорость чтения подстраивается под клиента. Избегать полного чтения тела, временных файлов и буферизации ответа в обратном прокси.
- Завершать работу с БД до начала передачи. Настроить тайм-ауты соединения и простоя, чтобы штатная загрузка большого файла могла идти дольше обычного JSON-запроса. При отключении клиента закрывать соединение с CDN.
- Если CDN сообщает длину, передавать `Content-Length` для отображения прогресса. При поддержке диапазонов проксировать `Range`, сохранять `206 Partial Content` и `Content-Range`, а для недопустимого диапазона возвращать `416`. Если CDN диапазоны игнорирует, клиент должен уметь перезапустить загрузку с начала.
- Для обычного скачивания отдавать `Content-Disposition: attachment` с безопасным именем файла. Если передача оборвалась после отправки заголовков, завершать поток как ошибочный и дать клиенту повторить запрос. Ошибки до отправки заголовков возвращать в обычном формате API.

### Сборка MP4 на сервере

Установите FFmpeg на сервере. По умолчанию приложение ищет `ffmpeg` в `PATH`. Другой путь можно задать через `RZK_FFMPEG`. Исходный MP4 и итоговый файл временно хранятся на диске. Для одного видео на 800 МБ потребуется около 1,6 ГБ свободного места. При ошибке или отмене временные файлы удаляются. Готовый MP4 хранится 10 минут с момента сборки, независимо от срока исходного тикета. Уже начатая передача может завершиться после этого срока.

WebSocket сообщает этапы `subtitles`, `downloading`, `muxing`, `ready` и `error`. Событие `downloading` содержит `received` и `total` в байтах. Если CDN не сообщает длину файла, `total` равен `null`. Событие `ready` содержит URL готового файла. Закрытие WebSocket во время подготовки отменяет операцию. Настройте прокси на передачу WebSocket Upgrade и направляйте выдачу тикета, WebSocket и скачивание в один процесс приложения. Один процесс обслуживает одну сборку за раз. Повторное скачивание готового файла в течение срока хранения использует уже собранный MP4. Исходные видео и субтитры также доступны отдельно.

### Нагрузка и выбор VPS

Для серии в 1080p размером 800 МБ VPS принимает около 800 МБ от CDN и отправляет около 800 МБ клиенту. Учитывать правила тарифа по входящему и исходящему трафику. При фактических 100 Мбит/с на всём маршруте передача займёт около 64 секунд без учёта накладных расходов. Длительность серии на время скачивания не влияет.

Для личного использования с одним или двумя одновременными скачиваниями начальный ориентир — 1 vCPU и 1 ГБ RAM. Бэкенд тратит CPU на HTTPS и пересылку. Его расход памяти складывается из памяти приложения и ограниченных буферов активных соединений. Выбор тарифа уточнить после замера реальной скорости между CDN, VPS и клиентом, а также пиковых CPU и RAM при параллельной загрузке.

### План проверки

1. Скачать исходный MP4 через RZK и проверить совпадение размера и контрольной суммы с ответом CDN.
2. Скачать ту же серию с субтитрами. Проверить переключение дорожки в целевых плеерах, синхронизацию на начале и конце серии и сохранение исходных аудио- и видеодорожек.
3. Проверить файлы с разным расположением `moov`, выбранные форматы субтитров, и отсутствующий язык субтитров.
4. Проверить отмену, отключение клиента, истёкший тикет, обрыв CDN и повторную загрузку. Проверить `Range` на CDN с поддержкой диапазонов и без неё.
5. Замерить пиковую память браузера и VPS, загрузку CPU и скорость при одном и двух одновременных скачиваниях файла на 800 МБ. Повторить с медленным клиентом и убедиться, что серверные буферы не растут с размером файла.
